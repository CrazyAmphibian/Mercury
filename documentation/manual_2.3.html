bytecode execution

mercury puts all data relevant to a function inside of its bytecode. this results in bytecode that uses up more space, however, it also means that the language is fairly simple to execute.

like any bytecode, mercury uses several different opcodes, each with a single, specific function.
unlike a low-level CPU bytecode, though, the opcodes do have a fair bit of flexability, and are actually just fancy functions.

typedef void (*mercury_instruction) (mercury_state* const M_CPP_restrict M);

//or, written in a more readable form:
void mercury_instruction(mercury_state* const M_CPP_restrict M) {

}

extern mercury_instruction mercury_bytecode_list[];

enum mercury_opcodes:mercury_opcode {
...
};

the mercury_bytecode_list is an array of opcode functions, and the enum mercury_opcodes gives a human readable way to index the array.
the sum execution of a single instruction is mercury_bytecode_list[opcode](state);

you may notice that unlike a C function, an opcode does not have any parameters other than state. This is because their operation is much more rigid, and most opcodes have a very specific, often single way of running.
