when to throw

throwing errors is useful, for if the user makes an unrecoverable mistake.
when writing your own functions, it is up to you to decide when to throw an error, though it is useful to stick to mercury's conventions to make it feel cohesive.

in general, mercury errors are almost always thrown because of a wrong type being provided, with other behavior either resulting in a nil or default value.
errors are also reserved for behavior that cannot reasonably be recovered from, such as running out of memory, or trying to divide an integer by 0.
other than that, providing too few function args is another common error reason.

errors for implicit behavior is generally discouraged due to the dynamic nature of mercury's code.
for example, string.sub will never throw an error if the provided range doesn't exist - as long as integers are provided, a string of some kind will be returned.
or string patterns, which will simply default to implicit behavior or ignore characters if the pattern is invalid.

upon a throw.

when an error is thrown, the following occurs:

  1. a relevant error message is put into stdout
  2. the current state's program counter is set to the end of the instructions
  3. the current state's errorcode variable is set
  4. steps 2 and 3 are repeated for each parent state of the current.
this means that throwing an error is quite disruptive, as it means halting execution of all code (unless you restrict the parent variable of a state, such as with rcall).

it is important to note that states will still need function variables unassigned manually when exiting, otherwise they will leak. the states themselves are cleared with every call, and so remaining stack or environment data will be properly freed.

how to throw

all error throwing code is contained in mercury_error.hpp/.cpp
the most basic error throwing function takes pointers as the error arguments.

void mercury_raise_error(mercury_state* M, const uint32_t errorcode, const mercury_int* data1 = nullptr, const mercury_int* data2 = nullptr, const mercury_int* data3 = nullptr);

do note that while the data args are typed as mercury_int*, the type they take can vary with the error code, and it is important to keep that in mind to not derefrence bad memory.

more throwing options

because some error codes want fairly static and consistent numbers as input, some variants of the error raising function were created

void mercury_raise_error_nonpointer(mercury_state* M, const uint32_t errorcode, const mercury_int data1 = 0, const mercury_int data2 = 0, const mercury_int data3 = 0);

void mercury_raise_error_firstargpointeronly(mercury_state* M, const uint32_t errorcode, void* data1 = 0, const mercury_int data2 = 0, const mercury_int data3 = 0);
