general typedefs

to make programming easier, and cross-platform, mercury uses some typedefs for basic types

#include <stdint.h>

#if INT64_MAX==INTPTR_MAX
  typedef int64_t mercury_int;
  typedef uint64_t mercury_uint;
  typedef double mercury_float;
  #define MERCURY_64BIT
#else
  typedef int32_t mercury_int;
  typedef uint32_t mercury_uint;
  typedef float mercury_float;
  #define MERCURY_32BIT
#endif


typedef uint16_t mercury_opcode;
constexpr size_t MERCURY_INSTRUCTIONS_PER_VARIABLE_SIZE = sizeof(mercury_int) / sizeof(mercury_opcode);

types are defined in an enum.

extern uint8_t M_NUMBER_OF_TYPES;

enum M_TYPE_ENUMS:uint8_t {
  M_TYPE_NIL = 0,
  M_TYPE_INT = 1,
  M_TYPE_FLOAT = 2,
  M_TYPE_BOOL = 3,
  M_TYPE_TABLE = 4,
  M_TYPE_STRING = 5,
  M_TYPE_CFUNC = 6,
  M_TYPE_ARRAY = 7,
  M_TYPE_FUNCTION = 8,
  M_TYPE_FILE = 9,
  M_TYPE_THREAD=10,
};

primative types

primitive types are stored as raw binary data. since all mercury types are of the same size, and the same size of a pointer on the system, a union is a logical compiler structure to use to group it together.

variables themselves (not their data) are almost always stored as a literal, and passed as a pointer.

union mercury_rawdata {
  mercury_int i;
  mercury_uint u;
  mercury_float f;
  void* p;
};
struct mercury_variable {
  uint8_t type = 0;
  mercury_rawdata data;
};

this handles nil, ints, floats, and booleans well enough, but complex datatypes use the pointer component of the rawdata and store the data there.

strings

strings are the simplest proprietary type, since they seek to solve the problem of C strings being null terminated, which isn't a terribly bad thing when you consider the historic reasons for it. regardless, this is how strings are stored

struct mercury_string {
  mercury_int size=0;
  mercury_uint refrences = 0;
  char* ptr = nullptr;
  bool constant = false;
};

the variable constant is used for an optimization, where the char* is managed by something other than the mercury runtime, or represents a constant character string that is baked into read-only memory.
do not make the mistake of setting a constant string to point to a function's instruction space, as when the function's lifetime ceases, the pointer will be invalid.

files

files are fairly straightforward, since they exist to act as a nice wrapper to obfuscate the gritty C backend of files and all the annoyances that can cause, plus, garbage collection.

#include <stdio.h>

enum M_FILEFLAGS :uint8_t {
  MERCURY_FILEFLAG_READ = 1 << 0,
  MERCURY_FILEFLAG_WRITE = 1 << 1,
};

struct mercury_filewrapper {
  mercury_uint refrences = 0;
  FILE* file;
  uint8_t modeflags;
};

threads

threads are the second type which are more or less just a wrapper, but here it's more justified because threads are not only more risky, but also system dependent.

#ifdef _WIN32
  #include <Windows.h>
#else
  #include <pthread.h>
#endif

struct mercury_threadholder {
  mercury_uint refrences = 0;
  volatile bool finished = false;
  bool customenv = false;
  #ifdef _WIN32
    HANDLE threadobject = NULL;
  #else
    pthread_t threadobject = NULL;
  #endif
  mercury_state* state = nullptr;
};

C functions

C functions are merely a classification of function with a particular syntax.

C function typedefs are not terribly readable, so here's it in proper written form

void function_name(mercury_state* const M_CPP_restrict M, const mercury_int args_in, const mercury_int args_out) {

}

tables

tables are the first truly unique mercury type. implemented as an array of variables and keys, seperated by type.

struct mercury_subtable {
  mercury_int size = 0;
  mercury_variable* keys = nullptr;
  mercury_variable* values = nullptr;
};
struct mercury_table {
  mercury_subtable* data;
  mercury_uint refrences = 0;
  bool enviromental = false;
};

when a table is created, data is allocated with a size to fit M_NUMBER_OF_TYPES elements, meaning that each type gets its own dedicated subtable.

from there, keys and values are stored in an array, which is resized according to the runtime's needs. because of this, tables are not very time efficient with large amounts of data. though, tables are made for sparse and mixed type data.

arrays

arrays are structured in a manner that is quite confounding, however it represents a real tradeoff being made. that being between spare data efficiency and access speed.

struct mercury_array {
   mercury_uint refrences = 0;
  #ifdef MERCURY_64BIT
     mercury_variable****** values = nullptr;
  #else
     mercury_variable*** values = nullptr;
  #endif
};

#ifdef MERCURY_64BIT
  constexpr int MERCURY_SIZE_SUBARRAY_1 = 0b1111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_2 = 0b1111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_3 = 0b1111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_4 = 0b1111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_5 = 0b111111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_6 = 0b111111111111 + 1;

  constexpr int MERCURY_WIDTH_SUBARRAY_1 = 10;
  constexpr int MERCURY_WIDTH_SUBARRAY_2 = 10;
  constexpr int MERCURY_WIDTH_SUBARRAY_3 = 10;
  constexpr int MERCURY_WIDTH_SUBARRAY_4 = 10;
  constexpr int MERCURY_WIDTH_SUBARRAY_5 = 12;
  constexpr int MERCURY_WIDTH_SUBARRAY_6 = 12;
#else
  constexpr int MERCURY_SIZE_SUBARRAY_1 = 0b1111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_2 = 0b1111111111 + 1;
  constexpr int MERCURY_SIZE_SUBARRAY_3 = 0b111111111111 + 1;

  constexpr int MERCURY_WIDTH_SUBARRAY_1 = 10;
  constexpr int MERCURY_WIDTH_SUBARRAY_2 = 10;
  constexpr int MERCURY_WIDTH_SUBARRAY_3 = 12;
#endif

a mercury array is a pointer to a pointer several times, until you get a pointer to variable.
this is because arrays are split up into bit ranges, as to not make setting a negative variable allocate several hundred GB of memory. this wastes some efficiency in dereferencing, but this solves the issue of semi-spare data, and keeps the access time linear with array size, since each index is based on the number.
the result is that in a worst case, one variable will allocate at most 100 kB on a 64 bit system.
